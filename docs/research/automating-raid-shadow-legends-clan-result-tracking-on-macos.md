## Bottom line

The most defensible and practical solution on **macOS** is **not** to chase an undocumented Plarium API first, and **not** to hook or patch the client. The strongest path is a **read-only companion app** that captures the RAID window on your Mac, runs **local OCR** on-device, and ships normalized JSON to your site and Telegram formatting pipeline. That recommendation follows from three things the public evidence makes clear: Plarium’s Terms prohibit reverse engineering and deriving code from the service; Apple gives you first-party macOS APIs for window capture and text recognition; and the existing RAID ecosystem proves that client-side data extraction is technically possible, but most mature tooling is either Windows-only, process-reading, or trust-heavy rather than a clean Mac-native export flow. citeturn8view2turn1search2turn1search17turn1search26turn20search0turn20search1turn26view0turn29view3

A second important conclusion is that **Hydra and Chimera are easier than Siege**. Plarium’s own guides say Hydra Clash and Chimera Clash totals are refreshed every 30 seconds, but the figures displayed in the clash UI are **rounded**; the **full exact** damage and clash-point values live in a tooltip in the **Battle Results** window. That means leader-side scraping of the clan overview is fine if you accept rounded values, but if you want exact integers you should capture closer to the player’s own result screen. Siege is less friendly because the public docs explain phases, Victory Medals, and member Victory Points, but do not document an equally clean “exact totals in a special tooltip” style surface for the whole clan. citeturn13view5turn13view6turn14view0turn14view2

## What the game publicly exposes

Plarium’s public documentation confirms that the information you care about **does exist in the game UI**. Hydra is a clan-only boss mode with weekly cycles; Hydra Clash runs weekly, shows clash points, refreshes its total every 30 seconds, and the exact full damage and clash-point values are available in a special tooltip in the Battle Results window rather than only in the rounded clash display. Chimera works similarly: it is clan-based, Chimera Clash is weekly, totals refresh every 30 seconds, and the exact full damage and clash points are likewise available from a Battle Results tooltip. citeturn13view0turn13view5turn13view1turn13view6

Siege is also formally documented, but the data surface is different. The official guide describes a Prep phase, Matchmaking, a two-day Battle phase, and a Results Calculation phase. It also says members gain or lose **Victory Points** from Siege battles, clans earn Victory Points for winning a Siege, and members can observe attacks on their fortress during Battle. That is enough to know there is result/state data in the client, but the public materials do not describe a neat public export surface or a documented per-member weekly results feed comparable to Hydra/Chimera’s result tooltip path. citeturn13view2turn14view0turn14view2

There are also broader clan-progression surfaces in the client. The Clans guide says the **Clan League** tab tracks progress tied to CvC, Hydra Clash, Chimera Clash, and Siege tasks. Separately, Plarium’s Leaderboards feature documents a current-season UI that updates every five minutes, which shows the client already maintains periodically refreshed ranking/result views in at least some modes. None of that is a supported export API, but it does reinforce the key point: the data is already rendered in the client frequently enough that capture-and-parse is viable. citeturn13view4turn13view3

## What existing tools actually prove

The existing third-party ecosystem shows that **reading RAID client state is technically possible**, but it does **not** give you a clean, low-risk, Mac-native clan-results extractor out of the box. HellHades’ optimizer is available for **Mac and PC clients running Plarium Play**, and HellHades explicitly says the extractor works by **reading your RAID account while it is open in Plarium Play**. Their troubleshooting materials also say the program may be flagged by security software because it needs to **read into an active process**, which is a strong sign that this class of tool relies on process-level introspection rather than official export. HellHades’ public changelog is still being maintained for current game updates, including support work posted in 2026. citeturn2search1turn2search5turn29view3turn29view2turn2search8

HellHades also proves another point that matters for your decision: once a tool has that account data, it can drive serious downstream automation. Their docs describe upload-to-website flows, direct in-game equip/sell features on supported configurations, and remote extraction/optimization flows. But for remote extraction, HellHades’ own FAQ says the user enters their **RAID account username, password, and Google-app 2FA code**, after which their service logs into the account to extract data. Even though HellHades says it does not store those credentials after extraction, that model is still much heavier than what you need for clan tracking, and it is not a pattern I would choose for weekly result ingestion. citeturn29view4turn28view0turn28view1turn28view2

Raid Toolkit is the clearest open-source example of a developer-facing local extraction stack. Its README says the SDK exists so tool authors do not have to deal with game updates and memory addressing directly, and its documentation says the RTK service watches for RAID processes, scans and updates account data, stores it locally, and exposes a **local WebSocket API** on `wss://localhost:9090`, including `getAccounts()` and `getAccountDump()` style access. But RTK’s own installation guide is explicit that it requires **Windows 10 or Windows 11** and ships as `RaidToolkitSetup.exe`, so it is not a direct macOS answer. citeturn6view0turn30view0turn30view1turn6view1

RSL Helper tells a similar story from another angle: it is a **community tool**, marked **Windows only**, and explicitly warns that third-party tools are used at your own risk and should follow the game’s Terms of Service. In other words, the community has proven that automation and client-adjacent tooling are possible, but the mature stack is Windows-centric and lives close enough to process automation that it should not be your first choice on a Mac main account. citeturn26view0

One more useful ecosystem signal: public clan-management apps aimed at RAID still advertise **screenshot upload** workflows for CvC, Siege, Hydra, and Chimera. That does not prove an API does not exist, but it is a strong hint that for clan-result tracking specifically, the public market still leans on capture and ingestion rather than a stable, openly documented export channel. citeturn25search0turn25search18

## How each extraction path looks on macOS

### Screen capture plus on-device OCR

This is the cleanest option on your platform. Apple’s **ScreenCaptureKit** is designed for high-performance capture of displays, apps, and windows on macOS, and Apple exposes window/app selection primitives through `SCShareableContent` plus single-frame capture through `SCScreenshotManager`. Apple’s **Vision** framework provides `VNRecognizeTextRequest` and a dedicated “Recognizing Text in Images” flow for OCR. In practice, that means you can build a helper that captures only the RAID window, crops known result regions, runs OCR locally, and emits JSON—without pyautogui, without external OCR services, and without shipping screenshots to an LLM. citeturn1search2turn1search17turn1search26turn20search0turn20search1turn20search4

For your exact use case, this path has another advantage: it matches the way the game already surfaces the data. Hydra and Chimera update their clash totals every 30 seconds, while exact values exist in the Battle Results tooltip; a capture helper can either read the clan overview periodically or grab the exact tooltip when it appears. That is a much smaller engineering problem than reverse engineering network payloads or maintaining a memory reader across client patches. citeturn13view5turn13view6

### Log-file inspection

This is the safest exploratory path before you write any code against the live client. Plarium’s own support documentation says that on Mac, Plarium Play stores logs under `\Users\username\Public\PlariumPlay\logs`. Those logs are officially documented for troubleshooting rather than structured gameplay export, so I would not assume they contain Hydra/Chimera/Siege result tables. But they are low-risk to inspect and may still reveal useful breadcrumbs such as endpoint hosts, timing, or client state transitions. citeturn19view0

### Network proxying

This is plausible but brittle. Tools like **Proxyman** and **Charles** can capture and decrypt HTTP/HTTPS traffic on macOS when the local machine trusts the debugging CA certificate; Charles explicitly describes SSL proxying as man-in-the-middle HTTPS inspection, and Proxyman documents HTTPS request/response interception on macOS. The problem is that apps using **certificate pinning** may reject the proxy certificate and fail to connect. Charles documents that behavior directly, and Proxyman’s troubleshooting docs say some protected apps cannot be intercepted for exactly this reason. So network proxying is worth a **contained experiment**, but it is not something I would choose as the foundation for your production workflow unless you verify early that RAID’s desktop client actually tolerates it on your machine. citeturn23search0turn24search7turn24search17turn24search1turn24search8

### Process memory or hooking

This is the path most likely to work technically and the path I least recommend for your stated constraints. HellHades and Raid Toolkit show that active-process reading can work, but Plarium’s Terms prohibit users from deciphering, decompiling, disassembling, reverse engineering, or otherwise attempting to derive code or underlying ideas from any part of the service. A Plarium moderator also said there are no officially approved clickers and that extra programs are not advised because they can harm the account. If your goal is a durable clan tracker on a main account, this risk/reward profile is bad. citeturn8view2turn9search0turn29view3

## The architecture I would actually build

I would build a **small native macOS companion app** with a deliberately narrow job: detect that the RAID window is visible, capture only the relevant window or region, OCR the known result blocks, normalize the text into your existing JSON schema, and push it to your website and Telegram formatter. Apple’s screen-capture and OCR APIs are already enough for that pipeline, and this keeps the system **read-only** from the game’s point of view. citeturn1search2turn1search17turn1search26turn20search0turn20search1

I would split the workflow into two modes. The first is **leader-side summary capture**: when you open the Hydra Clash, Chimera Clash, or Siege result screen you already screenshot today, the helper grabs that screen and converts it to JSON locally. This is the fastest path to replace your current manual screenshot-digitize-upload loop. The second is **player-side exact capture** for Hydra/Chimera only: because Plarium says the clash UI is rounded and exact values live in each battle’s result tooltip, the clean way to get exact per-run integers is for each clan member to run the helper and have it post their own result payload right after the battle finishes. If you only care about rounded public figures, you can skip this second mode. citeturn13view5turn13view6

I would also keep the UI interaction intentionally minimal. No auto-clicking, no battle automation, no library injection. A hotkey or a tiny floating “Capture RAID Results” button is enough. That removes the pyautogui pain you already ran into on macOS and avoids the need for any external OCR calls. Because the Hydra and Chimera clash interfaces refresh every 30 seconds, a hotkey-based capture is usually enough; if you later want full automation, you can add a lightweight polling loop that only activates when one of those tabs is visible. citeturn13view5turn13view6turn1search2turn20search0

For **Siege**, I would treat it as a second phase of the project rather than the first. The public docs confirm enough state exists to track the mode—Battle phase, Results Calculation, member Victory Point gains/losses, and live observation of attacks—but they do not expose an equally explicit exact-value result surface like Hydra/Chimera’s tooltip logic. So I would first replace your Hydra/Chimera pipeline, stabilize the OCR/parser stack, and only then add Siege-specific templates for whichever exact in-game summary pages your clan already uses operationally. citeturn14view0turn14view2

## Risk boundaries and what I would not do

I would **not** build against binary patching, injected libraries, or a Unity-hooking workflow on your main account. That is the zone most likely to drift into the reverse-engineering conduct Plarium explicitly forbids, and it creates ongoing maintenance work every time the client updates. The same goes for taking the HellHades remote-extraction model and repurposing it for clan data: even if the service says it discards credentials afterward, handing account credentials and live 2FA into a remote queue is a very different trust model from a local, read-only capture helper. citeturn8view2turn28view1turn28view2

I also would not spend much time trying to force **RSL Helper** into your environment. Its own site says it is Windows-only, and that matches the broader pattern in the ecosystem: when the tooling gets more invasive or more “smart,” it tends to become Windows-first. On Mac, you are better off leaning into Apple’s native capture/OCR stack than trying to port a Windows-style helper pattern. citeturn26view0turn30view0

If you ever decide you can tolerate a **Windows sidecar**—a spare mini-PC, VM, or remote box that runs RAID/Plarium Play—then Raid Toolkit becomes interesting because it already exposes a local developer API and account dump access. But that is a separate architecture and not the best answer to your current “I am on macOS and want the least shitty automation path” constraint. citeturn30view0turn30view1turn6view0

## Open questions and limitations

I did **not** find a publicly documented, officially supported **Plarium developer API** for exporting Hydra/Chimera/Siege clan results in the materials reviewed. Plarium’s public support surfaces focus on guides, FAQs, forums, and Discord/community resources rather than developer-facing export docs, so a supported external API appears unlikely from the public surface area I checked. That is an inference from the available materials, not an official “no API exists” statement from Plarium. citeturn1search9turn9search10turn10search7turn0search1

I also did not find a mature **Mac-native public tool** whose advertised purpose is extracting **weekly clan result data** for Hydra/Chimera/Siege directly from the client. The most relevant mature tools either focus on **account/gear/champion extraction** or are explicitly **Windows-only**, while clan-management apps still advertise screenshot-oriented workflows. citeturn29view3turn26view0turn25search0turn25search18

Because of the rounding behavior documented for Hydra and Chimera, one architectural question remains decisive for your implementation: **do you need exact integers or is rounded UI data enough?** If rounded values are acceptable, a leader-side OCR helper is enough. If exact values matter, the capture point probably has to move from “leader screenshots overview screens later” to “players capture their own results when the battle ends.” The official docs strongly support that distinction. citeturn13view5turn13view6
